## colors.rs → colors.dart
- Change: `MaterialColor` and `MaterialAccentColor` are colour extensions of their own that deref to painting's `ColorSwatch<i32>`; each `Colors` swatch is one of them, and it becomes a `Color` through `primary()` or an `AnyColor` through `into_any()`.
  Reason: language — dart:ui `Color` is a value here and cannot be subclassed, so `MaterialColor extends ColorSwatch<int> extends Color` cannot be one type (waft-painting's colors.rs entry).
  Affect: Dart's `Colors.red is ColorSwatch<int>` is true, but `extension::<ColorSwatch<i32>>()` finds nothing on a `MaterialColor`; only `extension::<MaterialColor>()` does.

## color_scheme.rs → color_scheme.dart
- Change: `ColorScheme`'s colours are plain `Color`s; a `MaterialColor` given to it, as `from_swatch` gives its `primary_swatch`, is stored as its primary colour.
  Reason: language — dart:ui `Color` is a value here and cannot be subclassed, and only the fields the framework resolves or type-checks carry an `AnyColor` (waft-painting's colors.rs entry).
  Affect: `ColorScheme::from_swatch().build().primary` equals `Colors::BLUE.primary()`, where Dart's `primary` is the swatch itself and equals only `Colors.blue`.

- Change: `_MenuAnchorState` is a base trait whose fields are a bag that `MenuAnchorState` and the menu bar's state carry, and `_MenuBarAnchor` holds the `MenuAnchor` it extends; `_MenuAnchorScope` holds the state erased.
  Reason: language — a Rust struct cannot extend another.
  Affect: a menu bar's anchor does not downcast to a `MenuAnchor`, where Dart's `is MenuAnchor` is true; a type lookup misses it in both.
- Change: `_MenuLayout` fits the menu into the whole overlay, with no avoid bounds and no display-feature sub-screens.
  Reason: platform — `DisplayFeatureSubScreen` needs `MediaQuery.displayFeatures`, which no host reports (Deferred).
  Affect: on a folded or hinged display the menu can straddle the hinge instead of keeping to the sub-screen nearest its anchor.

## dropdown_menu.rs → dropdown_menu.dart
- Change: `DropdownMenu::dropdown_menu_entries` is an `Rc<[DropdownMenuEntry<T>]>` that `did_update_widget` compares by pointer, so entries handed as a new list on each build count as changed on each build.
  Reason: language — Dart compares the list by identity and canonicalizes a `const` list, so a build that writes `const <DropdownMenuEntry>[…]` hands the same list every time; Rust has no constant heap values.
  Affect: a menu whose parent builds its entries anew on each build clears its highlight and filtered entries on each rebuild, where Dart's `const` entries keep them; a caller that keeps the `Rc` keeps them.

## chip.rs, chip_theme.rs, action_chip.rs, choice_chip.rs, filter_chip.rs, input_chip.rs → their .dart files (and generated/{chip,action_chip,filter_chip,input_chip}_defaults_m3.rs)

- Change: the forced-point `assert`s of `_RenderChipRedirectingHitDetection.hitTest` compare within f32 rounding, not exactly.
  Reason: platform — positions pass through Valo's f32 transforms in the hit-test result.
  Affect: a debug build accepts the rounded point where Dart asserts exact equality.

## date.rs → date.dart
- Change: `CalendarDelegate` and `DateTimeRange` have no type parameter: their dates are `waft_foundation::DateTime`.
  Reason: language — Rust has no subclasses of `DateTime`, which Dart's `CalendarDelegate<T extends DateTime>` ranges over.
  Affect: a non-Gregorian calendar maps its dates onto `DateTime`, and a delegate is held as an `Rc<dyn CalendarDelegate>`.
- Change: "today" is `DateTime::now()`, the UTC date.
  Reason: platform — waft-foundation's `DateTime` is UTC only, and no host gives a time zone.
  Affect: near midnight the highlighted day follows UTC, not the local zone.

## calendar_date_picker.rs → calendar_date_picker.dart
- Change: `YearPicker::new` has no `initial_date`, Dart's deprecated parameter that has no effect.
  Reason: language — a fluent widget has no deprecated, ignored setter to keep.
  Affect: code ported from Dart drops the argument.
